## Foundation C — editor and standalone player

Closes the Foundation A table's deferred rows (5, 6, 7 were settled in
Foundation B already; this closes 8, 9, 14) plus new decisions forced by
building the editor.

| # | Contract | Decision | Status |
| - | -------- | -------- | ------ |
| 8 | Game/editor module reload strategy | No live hot-swap. `PlayStopController::play()` always rebuilds the runtime scene fresh from the authored `Scene` via a JSON round-trip (serialize authored → deserialize into a separate runtime copy); `stop()` always fully tears down that runtime copy and discards it, restoring the authored scene untouched. A changed native module (`.so`/`.dll`) requires rebuilding it externally and relaunching the editor — the editor never calls `dlclose`/`dlopen` again on a module it already loaded while running, since any in-flight `PropertyDescriptor`/`Component` from the old module would outlive the unload. | Settled |
| 9 | Editor mode isolation | `PlayStopController` (`editor/editor_core/include/arcane_editor/editor_state.hpp`) owns the authored `Scene` and, only while playing, a second runtime `Scene` built by the JSON-round-trip above. The Inspector/Hierarchy only ever read/write the authored scene (and are `BeginDisabled` while playing, in `editor_main.cpp`); the Viewport renders whichever scene is active (runtime while playing, authored otherwise). Stopping discards the runtime scene outright, so edits made by gameplay code during Play (e.g. a script moving a node) never leak back into the authored scene — verified by `test_editor_state.cpp`'s "Play values don't leak after Stop" case. | Settled |
| 14 | Initial editor feature boundary | Shipped tonight: scene tree (Hierarchy: select/create/delete/drag-reparent), Inspector (transform + generic property-registry walk, "Add Component" from `ComponentRegistry::type_names()`), Viewport (offscreen-FBO render of the active scene via `SpriteRenderer`), Assets panel (lists project image files, click-to-assign a `Sprite::texture`), File > Save, Play/Stop toolbar. Deferred (doc explicitly treats these as "as capability grows", not Foundation C acceptance items): undo/redo, multi-select, grid snapping, multi-viewport/multi-camera editing. | Settled |
| 21 | Asset id scheme | No asset-database file. `asset_id_for_relative_path()` (`editor/editor_core/include/arcane_editor/asset_catalog.hpp`) is a pure function: FNV-1a 64-bit hash over the asset's path *relative to the project's `assets/` dir*. A `Sprite::texture` property just stores that integer. This means the same file always resolves to the same id across save/reopen/rename-of-project-dir without needing to persist a lookup table, at the cost that renaming or moving an asset *within* `assets/` changes its id (acceptable for now: no asset-rename UI exists yet to even trigger this). | **Delegated** — simplest option that satisfies the save/reopen acceptance test, no explicit instruction given |
| 22 | Native module destruction-order hazard | `editor_main.cpp`'s and `player.cpp`'s `main()` both declare `std::optional<GameModule> module` textually **before** `arcane::ComponentRegistry registry` and any `Scene`/`ProjectSession` that can hold module-originated `Component`s or `PropertyDescriptor`s. C++ destroys locals in reverse declaration order, so those must be destroyed before `module`'s destructor calls `dlclose`; getting the order backwards crashes with a `SIGSEGV` inside `std::_Function_base::~_Function_base` (confirmed by GDB during this work) because a `PropertyDescriptor`'s `std::function` closure's code lives inside the already-unloaded module. This is not enforced by the type system — it is a convention that must be followed by any future code adding a long-lived object that can hold module-originated closures/vtables. Documented here specifically so it isn't "simplified" back into a crash later. | Settled |
| 23 | Shared source-tree module copy vs. multi-toolchain builds | `samples/sample_game`'s `POST_BUILD` step copies the just-built module to `samples/sample_project/sample_game.so` (so a normal interactive run of the committed sample works without flags). This path is shared across every CMake build directory, so running gcc, then clang+ASan, then mingw in sequence (as `scripts/build-and-test.sh` does) leaves whichever built last as the file on disk — a gcc-built `arcane_editor`/`arcane_player` `dlopen`-ing a clang+ASan-built `.so` fails (`undefined symbol: __ubsan_vptr_type_cache`). Fixed with an explicit `--module <path>` CLI flag on both `arcane_editor` and `arcane_player` that each CTest entry sets to `$<TARGET_FILE:sample_game>` (that build's own module), bypassing the shared copy entirely for tests. **Pitfall reintroduced and re-fixed once already** during this work: `arcane_player`'s `Args` initially reused one `module_path` field (defaulting to `ARCANE_DEFAULT_MODULE_PATH`, itself `$<TARGET_FILE:sample_game>`) for both the legacy demo module and the `--project` override, so passing `--module` with that same default value was indistinguishable from "not passed" and silently fell back to the stale shared copy. Fixed by giving `--project` mode its own dedicated override field (`project_module_override`), matching the pattern `editor_main.cpp` already used correctly. The source-tree copy is gitignored and only used for manual/interactive runs, never read by CTest. | Settled |

| 30 | Game export layout | `scripts/export-game.sh OUT` (+ `install(... | 31 | Tilemaps | `Tileset` is a JSON asset (texture id, tile size, columns, tile_count; format_version 1; 1-based tile ids, 0 = empty; UVs derived from the grid so no texture size is needed). `Tilemap` is a component whose layer data is a single String property `layers` (`;` between layers, `,` between row-major ids), because `PropertyValue` has no array type and adding one is not worth it for this. ## FE10 — HUD Unicode text (delegated)

| # | Topic | Decision |
