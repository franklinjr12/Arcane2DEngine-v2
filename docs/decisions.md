Settled 2026-10-25, for `foundation-a-setup`. Contracts are the ones listed
in vision doc section 16, plus a few forced by implementation. Entries
marked **delegated** had no explicit instruction tonight and adopt the
doc's stated default leaning; the justification is why that leaning was
taken as-is rather than something else.

## Foundation C — editor and standalone player

Closes the Foundation A table's deferred rows (5, 6, 7 were settled in
Foundation B already; this closes 8, 9, 14) plus new decisions forced by
building the editor.

| # | Contract | Decision | Status |
| - | -------- | -------- | ------ |
| 8 | Game/editor module reload strategy | No live hot-swap. `PlayStopController::play()` always rebuilds the runtime scene fresh from the authored `Scene` via a JSON round-trip (serialize authored → deserialize into a separate runtime copy); `stop()` always fully tears down that runtime copy and discards it, restoring the authored scene untouched. A changed native module (`.so`/`.dll`) requires rebuilding it externally and relaunching the editor — the editor never calls `dlclose`/`dlopen` again on a module it already loaded while running, since any in-flight `PropertyDescriptor`/`Component` from the old module would outlive the unload. | Settled |
| 9 | Editor mode isolation | `PlayStopController` (`editor/editor_core/include/arcane_editor/editor_state.hpp`) owns the authored `Scene` and, only while playing, a second runtime `Scene` built by the JSON-round-trip above. The Inspector/Hierarchy only ever read/write the authored scene (and are `BeginDisabled` while playing, in `editor_main.cpp`); the Viewport renders whichever scene is active (runtime while playing, authored otherwise). Stopping discards the runtime scene outright, so edits made by gameplay code during Play (e.g. a script moving a node) never leak back into the authored scene — verified by `test_editor_state.cpp`'s "Play values don't leak after Stop" case. | Settled |
| 14 | Initial editor feature boundary | Shipped tonight: scene tree (Hierarchy: select/create/delete/drag-reparent), Inspector (transform + generic property-registry walk, "Add Component" from `ComponentRegistry::type_names()`), Viewport (offscreen-FBO render of the active scene via `SpriteRenderer`), Assets panel (lists project image files, click-to-assign a `Sprite::texture`), File > Save, Play/Stop toolbar. Deferred (doc explicitly treats these as "as capability grows", not Foundation C acceptance items): undo/redo, multi-select, grid snapping, multi-viewport/multi-camera editing. | Settled |
| 21 | Asset id scheme | No asset-database file. `asset_id_for_relative_path()` (`editor/editor_core/include/arcane_editor/asset_catalog.hpp`) is a pure function: FNV-1a 64-bit hash over the asset's path *relative to the project's `assets/` dir*. A `Sprite::texture` property just stores that integer. This means the same file always resolves to the same id across save/reopen/rename-of-project-dir without needing to persist a lookup table, at the cost that renaming or moving an asset *within* `assets/` changes its id (acceptable for now: no asset-rename UI exists yet to even trigger this). | **Delegated** — simplest option that satisfies the save/reopen acceptance test, no explicit instruction given |
| 22 | Native module destruction-order hazard | `editor_main.cpp`'s and `player.cpp`'s `main()` both declare `std::optional<GameModule> module` textually **before** `arcane::ComponentRegistry registry` and any `Scene`/`ProjectSession` that can hold module-originated `Component`s or `PropertyDescriptor`s. C++ destroys locals in reverse declaration order, so those must be destroyed before `module`'s destructor calls `dlclose`; getting the order backwards crashes with a `SIGSEGV` inside `std::_Function_base::~_Function_base` (confirmed by GDB during this work) because a `PropertyDescriptor`'s `std::function` closure's code lives inside the already-unloaded module. This is not enforced by the type system — it is a convention that must be followed by any future code adding a long-lived object that can hold module-originated closures/vtables. Documented here specifically so it isn't "simplified" back into a crash later. | Settled |
| 23 | Shared source-tree module copy vs. multi-toolchain builds | `samples/sample_game`'s `POST_BUILD` step copies the just-built module to `samples/sample_project/sample_game.so` (so a normal interactive run of the committed sample works without flags). This path is shared across every CMake build directory, so running gcc, then clang+ASan, then mingw in sequence (as `scripts/build-and-test.sh` does) leaves whichever built last as the file on disk — a gcc-built `arcane_editor`/`arcane_player` `dlopen`-ing a clang+ASan-built `.so` fails (`undefined symbol: __ubsan_vptr_type_cache`). Fixed with an explicit `--module <path>` CLI flag on both `arcane_editor` and `arcane_player` that each CTest entry sets to `$<TARGET_FILE:sample_game>` (that build's own module), bypassing the shared copy entirely for tests. **Pitfall reintroduced and re-fixed once already** during this work: `arcane_player`'s `Args` initially reused one `module_path` field (defaulting to `ARCANE_DEFAULT_MODULE_PATH`, itself `$<TARGET_FILE:sample_game>`) for both the legacy demo module and the `--project` override, so passing `--module` with that same default value was indistinguishable from "not passed" and silently fell back to the stale shared copy. Fixed by giving `--project` mode its own dedicated override field (`project_module_override`), matching the pattern `editor_main.cpp` already used correctly. The source-tree copy is gitignored and only used for manual/interactive runs, never read by CTest. | Settled |

## Foundation D — physics and input

Closes Foundation A's row 3 (units) and new decisions forced by Box2D and
input-action-map integration.

| # | Contract | Decision | Status |
| - | -------- | -------- | ------ |
| 3 | Pixel and physics units | Confirmed as recorded in Foundation A: **32 px = 1 m**. `PhysicsWorld` (`engine/src/physics.cpp`) converts at the simulation boundary only: `RigidBody2D`/`Collider2D`/`Transform2D` fields stay in pixels everywhere else in the engine (components, JSON, Inspector-equivalent code), and the y-flip between screen-space (y-down) and Box2D's y-up world is also confined to that same boundary code. | Settled |
| 24 | Physics runtime scope | `PhysicsWorld` only ever exists for a *runtime* scene: `PlayStopController::play()` (editor) and `arcane_player`'s `run_project()` each construct exactly one and call `rebuild()` once then `step()` every fixed tick; the authored scene in the editor's Edit mode is never handed to a `PhysicsWorld` at all, so the editor can never mutate authored transforms via physics (verified by `test_rebuild_without_step_does_not_mutate_scene` and `test_play_stop_isolation_with_physics`). | Settled |
| 25 | Input action map storage and live-binding | `InputActionMap` (bindings, not per-frame state) is serialized as a nested object inside `ProjectFile`/project.json rather than a separate file, since one project has exactly one action map today (`engine/include/arcane/project.hpp`). Gameplay code never receives an `InputActionMap&` through call parameters; instead a single global `arcane::active_input_map()` (set/cleared by the editor and player main loops, `engine/src/input.cpp`) is non-null only while Play is actually running, so a component's `on_update` can query actions without every lifecycle hook threading a reference through, while the editor's own ImGui input in Edit mode is never affected. | **Delegated** — simplest option satisfying "gameplay code queries actions", no explicit instruction given |
| 26 | Input backend abstraction | `InputBackend` is a tiny virtual interface (`is_down`, `mouse_position`) with two implementations: `GlfwInputBackend` (reads a real `Window`'s GLFW handle; gamepad codes come from `GLFW_JOYSTICK_1` only, no multi-gamepad support yet) and `FakeInputBackend` (tests set state directly, no window/platform input at all). This keeps `InputActionMap::update()`/`pressed()`/`held()`/`released()` unit-testable headlessly (`tests/test_input.cpp`) without a GL context. | Settled |
| 27 | Audio backend in editor/player | Both `arcane_editor` and `arcane_player` construct their `AudioSystem` with the **null backend** (no device opened; `play()` still records `AudioPlayCommand`s). Real-device playback has never been exercised on this headless box and is UNTESTED on native Windows/MSVC; switching is a one-argument change at the two construction sites once a game needs audible output. `play_on_start` AudioSources fire once when Play begins / the player loads (`start_play_on_start_sounds`); looping sources use the Music bus, others Sfx. | **Delegated** |
| 28 | Editor animation preview | Edit mode does not tick the scene, so the Toolbar's "Preview animations" checkbox calls `preview_animations()` (advances `AnimatedSprite` elapsed time only, which is not a serialized property, so previewing never dirties/changes the authored scene). Clips/sounds are assigned by clicking them in the Assets panel while a node with `AnimatedSprite`/`AudioSource` is selected. Clip/sound lists are scanned at startup (image list re-scans each frame; clip cache does not hot-reload). | **Delegated** |
| 29 | HUD text and layout | Text uses `stb_easy_font` (already in the pinned stb; ASCII-only stroke font drawn as quads through the existing `SpriteRenderer` with a 1x1 white texture) — the simplest option available, no new dependency; Unicode/glyph atlas is deferred. Layout is anchor (9 positions) + pixel offset in 720p-reference units, scaled by `screen_height/720` (`hud_layout`, pure and unit-tested). HUD lives in the engine runtime (not editor) and is drawn in the same frame after the world, so `SpriteRenderer::flush()` was added to switch to the screen-space camera mid-frame. | **Delegated** |
| 30 | Game export layout | `scripts/export-game.sh OUT` (+ `install(... COMPONENT game)` for `arcane_player` and `arcane_runtime`) builds/uses a build dir and produces `OUT/arcane_player`, the engine shared lib beside it (rpath `$ORIGIN` on Linux, DLL next to the exe on Windows), and `OUT/game/{project.json,scenes,assets,<module>}`. The module is copied under its real platform name and `project.json`'s `module` is rewritten to it (the committed sample says `sample_game.so`). With no `--project`, `arcane_player` runs `<exe dir>/game` if it has a `project.json` (exe dir via `/proc/self/exe` / `GetModuleFileNameW`, not cwd). `--mingw` also copies libstdc++/libgcc_s_seh/libwinpthread DLLs. An existing build dir is used as configured. No installer/packaging. | delegated |

## Toolchains actually exercised tonight

- gcc 14 Debug — required, must pass.
- clang 19 + `ARCANE_SANITIZE=ON` (ASan+UBSan) — passes.
- `x86_64-w64-mingw32-g++` cross-compile (`cmake/toolchains/mingw-w64-x86_64.cmake`), build-only, tests not run.
- All three driven by `scripts/build-and-test.sh`, which also runs `ctest` under `xvfb-run -a` for the two configs that run tests.

## MSVC: pimpl classes need out-of-line constructors (delegated)

Private `Window()`/`AudioSystem()` ctors are defined in the .cpp (where `Impl` is complete), and `/wd4251 /wd4275` are
added for MSVC: the engine DLL and its clients always share one toolchain/CRT, so those dll-interface warnings are noise.
